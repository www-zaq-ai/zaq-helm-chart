# PostgreSQL TLS

Application TLS and provisioning TLS are separate connections and settings.
Enabling one does not silently change the other.

## Image support and defaults

Published ZAQ **v0.19.0 and earlier lack application database TLS support**.
The chart keeps that image/default behavior unchanged: `database.tls.enabled`
and `image.databaseTlsSupported` default to `false`. The global minimum ZAQ
version remains v0.18.0; no future release number is assumed.

To enable application TLS, select a verified image containing the
[PR #943 implementation](https://github.com/www-zaq-ai/zaq/pull/943), including its
Python URL helper and libpq 17+. Set `image.databaseTlsSupported: true` as an
explicit operator attestation, not image inspection. TLS is rejected without
that declaration and for known unfixed official tags through v0.19.0. A tested
fixed/backported digest or custom image can declare the same semantic version.
Merging source does not replace a published image.

For a fixed image, the recommended application setting is **enabled**, meaning
certificate-chain and hostname verification with no plaintext fallback. Without
a CA Secret, ZAQ uses system trust. Private PostgreSQL CAs need the issuing CA
bundle, not an Ingress certificate, server private key, or password.

## Example: CA in the existing DBA Secret

Add a PEM CA bundle under `ca.crt` in the existing namespace-local DBA Secret,
alongside its externally managed `username`/`password` keys. No contents go in
Helm values. Select a real fixed image first; these custom image names are
placeholders, not published ZAQ artifacts:

```yaml
image:
  repository: registry.example.org/your-fixed-zaq
  tag: tls-fixed
  appVersion: "0.19.0"
  databaseTlsSupported: true
database:
  host: database.example.org
  tls:
    enabled: true
    ca:
      existingSecret: zaq-dba
      key: ca.crt
  provisioning:
    existingSecret: zaq-dba
    sslMode: verify-full
preflight:
  enabled: true
  sslMode: verify-full
```

Prefer an immutable digest in production. The database hostname must match its
certificate's DNS identity, not an unrelated Service alias or IP address.
For system trust, leave `database.tls.ca.existingSecret: ""`. The CA key mapping
defaults to `ca.crt` and is used only with a selected Secret. With provisioning
disabled, a CA Secret can still be selected independently, including a DBA
Secret used only for its CA key; no DBA credential references are then injected.

## Connection-specific configuration

- **Application and migrations:** `database.tls.enabled` supplies exactly
  `ZAQ_DATABASE_SSL=true` or `false`. When enabled with a custom CA, it also sets
  `ZAQ_DATABASE_SSL_CA_CERT_FILE=/etc/zaq/database-ca/ca.crt`.
- **Init container's application-owner URL check:** gets those same application
  settings. ZAQ constructs the owner URL and converts its TLS options to libpq
  for that check, preserving receipt/identity validation.
- **Provisioning DBA and separate owner/reader psql checks:** retain independent
  `database.provisioning.sslMode`, default `prefer`. Choose `verify-full` for
  certificate and hostname verification; application TLS does not override it.
- **Optional preflight:** retains independent `preflight.sslMode`, default
  `prefer`. It is a read-only libpq check, not an Ecto TLS guarantee. It forwards
  `PGSSLROOTCERT` into its sanitized subprocess environment.

Both libpq settings accept `disable`, `allow`, `prefer`, `require`, `verify-ca`,
and `verify-full`. `prefer`/`allow` permit plaintext fallback; `require` is not a
hostname-verification policy. A selected CA supplies the mounted path as
`PGSSLROOTCERT`; otherwise verification modes use `system`, requiring libpq 17+.
Provisioning and preflight share the selected CA even with application TLS off.
No application CA-file variable is emitted while application TLS is disabled.

The chart keeps `DATABASE_URL` generated by ZAQ's image entrypoint. It exposes
no credential-bearing URL override and duplicates no URL translation or SQL.
TLS names stay reserved from custom environment overrides. TLS does not change
the v0.19.0 owner `CREATEROLE` requirement or automate
[DBA upgrade maintenance](deployment.md#upgrading-the-v0180-owner-contract).

## Secret projection and lifecycle

The volume projects **only the selected CA key**, mapped to `ca.crt`, read-only
with mode `0444`. Reusing the DBA Secret does not mount its username/password
keys into the application. Init/preflight credentials retain individual
`secretKeyRef` mappings. Known DBA/runtime credential keys are rejected as CA
selections. The chart cannot inspect Secret contents: operators must select a
PEM CA bundle, not copied credentials. No Secret creation, lookup, or RBAC is
introduced.

Missing CA Secrets/keys block volume setup; inspect Pod events. A container that
cannot start has no custom TLS log. Preflight retains its bounded Job deadline
and cleanup policy. Otherwise Helm `--wait`/timeout and readiness surface startup
failures. Wrong, expired, malformed, or untrusted certificates and hostname
mismatches fail instead of downgrading verified application TLS.

CA rotation remains external. Projected files may refresh, but the chart does
not promise live pool reload or trigger a rollout on Secret-data changes.
Restart application Pods after coordinated CA rotation; subsequent init/hook
runs use the current bundle. Helm rollback does not reverse database migrations.

## Validation

Offline tests cover schema failures, image gating, CA-only DBA-Secret projection,
credential-key rejection, independent modes, form mappings, and preflight CA
forwarding. See [development checks](development.md). The opt-in real Kind suite
uses `ZAQ_TLS_TEST_IMAGE` for a locally built fixed image and an SSL-required
disposable PostgreSQL, never an existing database. It checks real migrations,
SSL sessions, readiness, provisioning, receipt restart, app-only upgrade, rejected
CA/hostname/plaintext/expired certificates, missing keys, and system trust.

At PR head `8cfd6f9db57e3d00b8c352cac473ab689301b305`, the upstream Docker ignore
allowlist omits new `scripts/database_url.py`. Production image packaging must
include it. Local chart tests can use a test-only build-context allowlist
correction without changing application code; this does not prove the
uncorrected upstream Docker packaging builds successfully.
